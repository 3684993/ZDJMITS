## 二、目标架构与职责

`低频资产治理 → Approved Universe(~100 underlying) → 轻量常驻行情/机会索引 → Hot Candidate Pool(20～30) → 新事实+容量触发 → 单27B Primary → 现有Entry Manager → 交易所事实 → TP/对账/生命周期`

9B走旁路：非结构化外部资料 → 引用和数值抽取 → 确定性校验 → 可选上下文；不拥有方向、资金、暂停或下单权限。

### 1. Approved Universe：长期资格，不是即时机会

- 目标约100个**独立underlying**，默认容量100；质量符合者不足100就如实保留较少数量。USDT/USDC是同资产的可选执行合约，不计两份资产。
- 保留并迁移现有V4绝对底线：24h成交额和30日中位日成交额各≥2000万美元、日成交笔数≥20000、OI≥500万美元、上市≥180天、历史≥25天、综合流动性≥0.2；相对校准只能提高门槛。BTC/ETH有优先覆盖，不能绕过合约可交易性、黑名单和数据有效性。
- “高流动性”不等于“优质项目”。补充可追溯的资产身份/合约映射、上市与下架风险、项目类别和集中风险治理；缺失资料标REVIEW_REQUIRED。禁止用模型印象或短期涨幅自动批准，也不在本计划虚构100币名单。
- 首次迁移对83项逐项输出：旧批准、V4复核、来源、时间、拒绝原因、持仓影响。旧V3不得无期限豁免；只限制失格资产新Entry，管理中的仓位/退出保留。
- 之后每日增量检查交易状态/证据到期，每周完整复核；黑名单、下架和重大事实触发即时更新。目录不可变版本+内容哈希+生效时间，资格发布与采集解耦。单来源失败保留未过期可信版本并降级，过期后停止相应资产新增风险，不全局清空。
- 修正研究review的30日样本：排除未闭合日K，日期连续且去重；单标的请求失败不能使整批无结果。候选预筛不能长期只看当天成交额Top120，应加入旧Approved保留集，避免核心资产因平静行情掉队。

| 层 | 数据/频率 | 预算与边界 |

| Hot完整层 | 默认20、弹性最多30：新鲜执行盘口、最近5分钟成交价、闭合1m/5m/15m及必要高周期历史；高周期只在闭合/修订时更新 | 先沿用默认20，不自动改变现有poolMax24；扩到30须单独配置确认。采用闭合bar缓存，REST只预热/补洞，不整套定时重拉 |

**最小实现选择：沿用MarketDataHub和Provider接口，增加采集等级/订阅差异和闭合bar缓存；不先建多进程行情平台。** 轻量1m闭合序列可按交易所UTC边界聚合5m/15m，必须完整、连续并与交易所REST抽样校验；缺一根不得合成“完整K线”。高周期直接低频缓存交易所闭合数据。

Hot状态为WARMING/READY/WAIT_OPPORTUNITY/ANALYZING；持仓和活动Entry迁入管理集合，新币预热成功才替换，禁止先清池后重建。保留现有replacementDelta作为初始滞回、最低驻留时间及单轮替换上限2；即使未达替换分差，也允许因失格、占用或长时间无候选补位。按准备状态、执行流动性、变化幅度及等待年龄排序，不设置固定SHORT偏好。

轻量索引只对变更资产更新；全量排序允许低频校准，不允许每次报价/每2.5秒重新做全市场质量治理。CORE饥饿保护按underlying计算。满仓、无信号、可执行余额不足分别显示WAIT_CAPACITY/WAIT_OPPORTUNITY/WAIT_FUNDS；行情、TP、对账、研究和已授权订单管理继续运行。

供应SLO：若合格且未占用资产足够、资金与数据健康，Hot维持目标20，温热备用不少于5；READY耗尽后60秒内开始补齐、120秒内完成可恢复补位。不可满足时必须输出质量/合约/占用/预热/限流分类及下一检查时间，不能伪造READY或为凑20降低质量。

### 3. 两个模型

- 单27B槽位不变。只有新闭合bar、具有经济意义的价格区间变化、明确WAIT触发、资格/权限实质变化，且数据齐备、无同underlying活动Entry、具备当前预算时提交新Primary。
- contextKey由相关配置内容哈希替代所有Settings版本号；排除主题、日志设置和无实质变化的启动版本增长。使用幂等键`环境/账户/underlying/contextHash`，跨重启仍去重。
- 未变事实不得重推；模型无信号是合法等待，不能转PLACE。授权尚有效的执行队列独立续行，不被新分析准入WAIT撤销，也不能绕过真实资金/重复单等硬阻断。
- 9B只对需要语言理解的新外部事件工作。现有enqueueMarketChanges把5分钟bucket纳入hash，会让事实未变仍产生新任务；去重以来源事件版本和语义事实变化为主，禁止仅因时间窗滚动调用9B重复“提取”已有结构化趋势。
- 当前feedToPrimary=false，不得把9B任务数当决策贡献。先离线比较有/无外部上下文，验证引用、数值、时间可用性、冲突与注入防护；只有质量增益且延迟预算可接受才另行启用。9B空闲不构成故障，不新增Scout/Shadow审批层。

## 三、分阶段实施顺序与PASS标准

### P0-A：证据修正与HTTP故障定位

1. 锁定实际PID、源码/构建、Settings哈希、DB输入快照、环境/账户指纹；读取当前状态，不沿用本文件时间点数字。保护所有用户改动。
2. 重算91样本：保留9次池内缺口及1次observer子进程查询失败；该失败不是HTTP超时。观察脚本并行取pipeline/snapshot，可能跨观察版本，需单一原子诊断输出。缺样本和探针故障分别记UNKNOWN，不能作为PASS或交易系统失败。
3. 故障链分层：loopback、LAN地址、用户浏览器/代理；分别记录TCP connect、HTTP首字节、完整响应、请求路径和关联ID。明确服务端是否收到请求。服务端有持续日志只能排除“进程完全停止”，不能排除间歇事件循环饥饿。
4. 加轻量liveness与独立cached readiness：请求路径禁止同步数据库全表统计、integrity扫描、源码哈希或外部网络调用。DB健康记录最近真实检查时间，未检查为UNKNOWN；历史计数和汇总异步增量维护。
5. 采样event-loop delay、CPU/RSS/堆、队列等待、SQL与投影耗时、FS写入耗时。依证据选择修复：同步CPU迁出热路径、写队列有界、失效广播合并、查询索引/分页；确有CPU瓶颈才使用单个worker做纯计算，禁止多个worker写主库。
6. 在独立端口/独立数据的真实规模副本复现：同步日志/审计、行情峰值、两个浏览器标签、Brain搜索详情、慢网络同时发生。必须能指出失败调用链与修复前后对比。

PASS：同机压测liveness P99≤100ms，主要API P95≤250ms/P99≤1s，HTTP超时0；event-loop P99≤100ms且无>1s阻塞；浏览器页面和详情可用≤2s。至少2小时覆盖历史规模和并发维护。若无法复现历史挂起，标“原因未证实”，用连续观测关闭风险，不能写“根因已修复”。

### P1-D：Testnet连续终验

发布只能在用户明确授权的维护窗口，用规定手动脚本；不自动重启。新版本/风险相关配置/Prompt/Fact或关键数据契约变化产生新基线。界面主题变化不应无故重置交易证据。

24h为连续观测而非冻结交易。100生命周期定义为100个不同授权链，分别报告：授权→未提交终结、已提交→交易所终态、成交→退出闭环；不把REJECT、同单重报价、多个fill碎片当多条。**准入100项须为已提交订单的终态生命周期**，其中至少20项有自然成交；其中至少5 LONG、5 SHORT，并至少5个完整退出闭环。其他罕见分支由隔离故障注入补覆盖，不能冒充自然样本。

### 生产前必须签收的硬门

1. **账户/环境**：生产/Testnet独立密钥命名空间、DB、clientOrderId归属和日志；应用写许可绑定具体环境、账户、host与预算。当前`assertTestnetExchangeWrite`不能删掉了事；独立Canary许可未签发前Production默认锁定。
2. **管理面**：局域网可达不等于授权；提供身份认证、写操作授权、CSRF/Origin校验、敏感数据脱敏和审计；公开health只给最小状态，不暴露账户资产。无外网裸露管理端。
3. **合约/费用/时钟**：以生产exchangeInfo过滤器为准，不用pricePrecision/quantityPrecision替代tickSize/stepSize；核验费率、费率资产、funding、滑点和名义上限。以多个样本估算时差并监测漂移；clock超过安全预算不能伪造可用。
4. **仓位模式/退出**：Hedge必须对应positionSide，不能照搬One-way的reduceOnly参数。人工LIMIT退出即使预计亏损也进入合法执行流程；交易所拒绝、断网或不合法参数必须明确失败，不得伪成功。LIMIT不保证立即成交，因此必须明确无法成交时的告警、人工接管和用户批准的风险处置；没有可验证的退出预案不得Canary。
5. **保护与恢复**：TP覆盖不等于限制下行损失。现有损失/暴露限制继续有效；若无自动止损授权，必须明确对应风险和人工响应边界，不擅自新增Market策略。恢复/回滚不得丢失真实成交、改变方向或重复下单。

官方接口依据：生产规格应读取过滤器而非精度字段，见[Binance Exchange Information](https://developers.binance.com/docs/derivatives/usds-margined-futures/market-data/rest-api/Exchange-Information)；Hedge的positionSide及reduceOnly限制见[Binance New Order](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/New-Order)。实施时核对当日官方文档与账户实际权限；本轮未访问生产私有账户。

## 六、发布、回滚及进度定义

### 发布/回滚

- 代码、目录、数据契约分别版本化；保留旧Approved快照、迁移差异、构建哈希和一致性备份。先在隔离副本验证旧schema兼容或向前恢复，不做“覆盖旧dist+旧DB”式回滚。
- 发布前提交具体变更与验证结果，随后才申请该次Engine生命周期授权；只能用scripts/start-zdj-lan.ps1手动启动，不安装任务/服务/重启守护。
- 运行故障首先阻断**受影响范围的新风险**，保留已有订单/TP与对账；是否撤未成交订单、减仓必须遵循已批准策略，不因UI或模型故障盲取消合法单。
- 软件回退保留最新交易账本：先核对交易所订单/成交水位和clientOrderId，再迁移兼容状态；UNKNOWN未查明不释放占用。旧备份只用于恢复验证，不能覆盖备份之后的真实事实。
- Approved回退不能恢复已被黑名单/下架否决的资产；采集层退回兼容路径也不得牺牲订单维护预算。Production许可失效回到只读/禁止新Entry，不影响获授权的必要退出管理。

### DONE / PENDING / BLOCKED

- **DONE**：该项代码/配置或操作已实施，对应构建与原始证据可回读，正反场景通过；注明离线、Testnet、Production哪个范围。
- **PENDING**：实现可用，但时间、自然样本、连续窗口未满足；列起点、实际样本和剩余数量，不能以计划完成代替验收完成。
- **BLOCKED**：缺具体生命周期/资金授权、生产只读账户、退出方案，或存在未解决缺陷；列阻断证据、负责人和解除动作。其余独立工作继续。
- 项目只有在T1完成且P0/P1生产只读硬门通过、C0授权参数齐全时，才能称“具备进入Canary条件”；Canary本身未验收不能称实盘全面收尾。

### 交付合同与工作量

每阶段一份小型变更集、一份机读验收JSON和更新后的矩阵；复用现有测试，不机械重复全部历史流程。建议P0-A优先，P0-B/C随后集中交付，T1自然观察；生产只读设计可同期准备，生产操作依矩阵逐级授权。初步工程量约4～7个专注工作日，加至少24h自然观察；这是待故障复现修正的估算，不承诺一晚完成或固定模型tokens。

可延后：自动扩展超过100资产、跨交易所、复杂新闻Agent、第二Primary、强制9B在线、收益优化搜索、全系统微服务化。不得让这些扩展挡住当前HTTP、资格和事实一致性收尾。
