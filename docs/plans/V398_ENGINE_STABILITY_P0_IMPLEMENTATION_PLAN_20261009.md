# V3.9.8 Engine stability P0 implementation plan

**Evidence baseline:** `b5db4710c6cc4d7be6f0af0b7c744bef242c4ef0`. Forensic report: [`INCIDENT_FORENSICS_REPORT.md`](../reports/v398-engine-stability-p0-20261009/INCIDENT_FORENSICS_REPORT.md).

**Current root-cause status:** `PROCESS_EXIT_CRASH` is proven by PID 8524's recorded `0xC0000409` exit. The fail-fast subcode, module, stack, and triggering operation are unavailable; do not label any application feature, V8 tier, settings update, SQLite operation, or model/network service as the cause. This plan therefore authorizes only an offline diagnostic enhancement; it does not claim to fix the native failure.

## Phase R2 — bounded diagnostics only, offline

1. Add a read-only Windows evidence collector under `scripts/` with a deterministic fixture-driven test. Its inputs are an explicit PID/instance/build/source identity, UTC/+08 interval, and known local log paths. It must not discover or contact unrelated processes, call Engine HTTP endpoints, inspect SQLite, access exchange credentials/settings payloads, change WER/registry/policies, collect full dumps, or start/stop any process.
2. Bound every source: target only Application/System events in the requested interval and relevant providers/PID; stream only the matching Engine JSONL identity; inspect launcher/process lifecycle rows for that PID; record log byte counts, last-write times, SHA-256, query counts, skipped sources and error reasons. Keep raw Windows event text and complete runtime logs in a local-only evidence directory. Emit a public-safe summary with process start/parent/exit status, last structured event, first failed/last known successful observation, event-log match counts, source coverage and `UNKNOWN` gaps. Redact account/credentials, complete settings values, client/exchange order IDs, order payloads, AI prompts and symbols where not necessary for incident classification.
3. Classification is evidence driven and independent: exact nonzero Windows fatal status plus matching PID is `PROCESS_EXIT_CRASH`; a live PID with failed HTTP is `PROCESS_ALIVE_HTTP_UNAVAILABLE`; exit 0 or a documented shutdown action is only `PROCESS_EXIT_NORMAL_OR_EXTERNAL` when supported by matching records; otherwise `UNKNOWN`. Do not infer normal exit from a missing listener. Treat missing/mismatched clocks, event-log gaps, log truncation and missing dump as explicit coverage gaps. Preserve Windows Resource-Exhaustion-Detector Event ID 2004 as a distinct system-level low-virtual-memory fact; it is not PID-specific unless that PID is present in the event's process list, and does not establish causality without same-PID samples or fault evidence.
4. Add deterministic fixture tests for: matching fail-fast receipt; ordinary nonzero exit without crash evidence; graceful shutdown; child still alive while HTTP is unavailable; PID reuse/identity mismatch; low-virtual-memory Event ID 2004 with and without PID match; absent or truncated logs; missing event-log access; secrets/private payload redaction; and bounded output. Verify the collector never writes to live data, SQLite, Engine configuration, Windows policy, or exchange interfaces.
5. Do not modify `apps/engine` trading, scheduler, reconciliation, Settings, database, worker, market/AI or order paths until a dump/stack, native diagnostic or reproducible isolated test names a code-level trigger. In particular do not change Node/V8 flags, add blanket exception handlers, disable safeguards, delete/backup live SQLite, or introduce a restart/watchdog path.

## Phase R2 delivery gates

- Work only in the clean isolated worktree based on this exact main SHA; preserve `D:\MITS` and its dirty/untracked inventory.
- Run the collector's targeted fixture suite and the repository's complete `npm run verify`; capture complete stdout/stderr and failures to files, and report actual counts. Do not launch Engine or use real TESTNET/production exchange writes for a test.
- Publish the implementation/report and sanitized fixture summaries. Fetch the pushed commit independently and verify HEAD plus SHA-256 for each published file. Query GitHub Actions by exact head SHA; `in_progress`, `failure`, missing jobs, or API errors are not SUCCESS.
- Result may be `DIAGNOSTICS_READY_NOT_DEPLOYED`; it cannot be `CODE_FIXED_RUNTIME_NOT_ACCEPTED` because no code-level crash trigger is currently proven.

## Phase R3 — separate authorization and actual runtime acceptance

Nothing in R0–R2 authorizes Engine lifecycle changes. Ask for a separate, narrowly scoped authorization before any WER configuration/trace installation, foreground diagnostic start, verified-build deployment/start, long-duration observer, or controlled recovery. The authorization must specify allowed action, exact Engine/source identity, TESTNET-only constraints, observation duration and resource budget.

After that authorization, use one verified start, close the PID/parent/instance/build/source/exit receipt chain, preserve local dump and event-log evidence, and separately sample API, event-loop latency, scheduler, private/market truth, TP and order identity, SQLite lock/health, worker and commit/memory/handle pressure. Keep startup and steady-state windows distinct. A 5–10 minute run is screening only. Stability can be accepted only for a user-approved continuous window (at least 24 hours for the proposed long-window acceptance) with no unexplained exit, critical fact/TP gap, order-identity `UNKNOWN`, unsafe restart, or test/prod boundary violation, and with adequate telemetry coverage. Any failure returns the task to forensics; recovery or a later READY does not erase it.

Until such evidence exists, the only honest runtime status is `RUNTIME_ACCEPTANCE_PENDING`; after R2, the code-delivery label is at most `DIAGNOSTICS_READY_NOT_DEPLOYED`.
